# Atlas backend

This is the first real slice of Atlas's backend — not a demo, not simulated
in the browser like `web/`, but actual TypeScript implementing the
architecture from `docs/research/atlas-protocol-research.md` (§9 spend
delegation, §10 payment infrastructure). It's a start, not a finished
system — see "What's next" below for exactly where it stops and why.

## What's real vs. what's a stub

Everything under `src/domain/` and `src/services/` is real, working,
type-checked, unit-tested logic with no placeholders:

- **`domain/money.ts`** — integer minor-unit arithmetic. No floats anywhere
  in this codebase's handling of money, on purpose.
- **`domain/ledger.ts`** — the double-entry engine. Every movement of value
  is a transaction whose entries must sum to zero per asset. A balance is
  always computed as a sum over entries, never stored as a mutable field —
  see the schema comment on why this is what actually resolves "balances
  shouldn't be treated as a pooled value," independent of whether the
  underlying custody wallet is pooled.
- **`domain/permissionGrant.ts`** — velocity limits, single-use enforcement,
  expiry, and the rule that a connected wallet can never be a funding
  source (attestation only — see the research doc's §5/§9).
- **`domain/auth.ts`** — every authenticated request is signed with the
  identity's own Ed25519 private key, verified against its stored public
  key. No password, no session cookie, no bearer token anywhere in this
  codebase — this is "identity is a keypair" (§1) applied to API auth, not
  just a UI idea. Includes real replay protection: the timestamp is part of
  what's signed, so a captured signature stops verifying once the clock-skew
  window closes. See `test/auth.test.ts` for real generate/sign/verify round
  trips, cross-identity rejection, and tamper detection — no mocked crypto.
- **`services/settlementService.ts`** — the full card-funded-purchase flow:
  charge the funding source, buy crypto from a liquidity partner, allocate
  the position, hold it, and either release or reverse it. `reverseSettlement`
  is the literal implementation of the fraud/chargeback accounting worked
  through in §10 — see `test/ledger.test.ts` for the two scenarios (caught
  in time vs. too late) proven numerically.
- **`services/spendTokenService.ts`** — issuing and redeeming `SpendToken`s
  (Transaction B from §10: a token actually getting used somewhere),
  redemption draws down the same grant allowance a direct purchase would.
- **`services/withdrawalService.ts`** — moving a released position out of
  Atlas to an external address, refusing to move more than the identity's
  real ledger balance.

Everything under `src/adapters/*/stub.ts` is an **explicitly marked
placeholder** for a real provider integration, used when no real credentials
are configured:

| Adapter | Real provider this becomes | Status |
|---|---|---|
| `adapters/funding` (bank) | An Open Banking / PISP provider (TrueLayer, Tink) | Stub only — no provider account yet |
| `adapters/funding` (card) | Stripe | **Real implementation exists** (`stripe.ts`) — used automatically when `STRIPE_SECRET_KEY` is set, see `adapters/funding/factory.ts`; falls back to the stub otherwise |
| `adapters/custody` | An MPC wallet provider (Turnkey, Privy, Fireblocks) | Stub only — no provider account yet |
| `adapters/liquidity` | A real exchange API or Circle | Stub only — illustrative fixed rates instead of a live market |

The whole point of the adapter boundary (an interface in `types.ts`, a stub
or real implementation behind it) is that nothing above this layer — the
services, the API routes — needs to change when a real provider gets wired
in or swapped out.

### Real blind-signature SpendTokens

This used to be the codebase's most honest documented gap: token issuance
generated an opaque random reference (real tokenization — merchants never
see the underlying funding source), but Atlas's own database still stored a
direct token→grant link, which quietly defeated §9's "Atlas can't correlate
a spend to the grant that funded it" claim. That's no longer true.

`domain/blindSignature.ts` implements real RSA blind signatures (Chaum's
construction) with actual BigInt modular arithmetic over a real RSA keypair
generated by Node's own `crypto` module — not a placeholder. `test/blindSignature.test.ts`
proves it works: a full blind → sign → unblind → verify round trip, a
demonstration that blinding the same token twice produces two unrelated-looking
values (the actual unlinkability property, not just an assertion of it),
rejection of forged messages, and rejection across different issuer keys.

The schema was redesigned around this rather than bolting crypto onto the
old shape: `SpendTokenIssuance` records that a token was issued against a
grant (needed for velocity limits — see below for why that check has to
happen at issuance, not redemption), and `RedeemedSpendToken` records that a
token was spent, keyed only by a hash of the token value. **The two tables
share no foreign key** — there's no column in the schema that could join
them, which is what makes the unlinkability structural rather than a policy
choice the application code happens to follow.

Two honest limitations, stated plainly rather than glossed over:
- This is a correct implementation of the underlying construction, not a
  hardened one — a real deployment should use a padded, standardized scheme
  (RFC 9474) to close known malleability issues in plain textbook RSA
  blinding. The protocol shape stays the same either way.
- The signed token doesn't cryptographically bind a specific amount, so the
  amount is checked against the grant's allowance at *issuance* (the one
  point where request and grant are still linked) but trusted at face value
  at *redemption* (deliberately, since nothing there can be checked against
  a grant anymore). A complete system closes this with a separate issuer
  key per denomination, the classic Chaumian e-cash approach — not
  implemented here. Both limitations are called out in `spendTokenService.ts`
  and `domain/spendToken.ts` directly, not just here.
- The issuer's private key currently lives in the signing process's memory
  only, generated fresh on first use — real deployment needs this behind a
  KMS, not regenerated per restart (tokens issued in one process lifetime
  become unverifiable after one that doesn't share the key).

`scripts/smoke.ts`'s third scenario plays both the client and Atlas roles
explicitly (clearly labeled which is which) to demonstrate the full
protocol, including a redemption and then a rejected double-spend attempt
against the same token.

### Stripe, concretely

`adapters/funding/stripe.ts` implements real off-session `PaymentIntent`
charges against a saved `PaymentMethod`. A `FundingSource.externalRef` for a
Stripe-backed card is `${stripeCustomerId}:${stripePaymentMethodId}` — the
card itself is captured client-side via Stripe Elements and never touches
this backend; Atlas only ever stores what Stripe hands back. `routes/webhooks.ts`
receives real `charge.dispute.created` events (verified against
`STRIPE_WEBHOOK_SECRET`, Stripe's own signature scheme — not an Atlas
identity signature, since Stripe is the caller) and calls
`settlementService.reverseSettlement` automatically — this is what closes
the loop between "a real dispute happened, weeks later" and the ledger
actually reflecting it, per §10.

### Authenticated routes

Every route except `POST /identities` (registration — see below),
`GET /health`, `POST /webhooks/stripe` (authenticated differently, by
Stripe's signature, not an identity's), and `GET /spend-tokens/issuer-key`
(public by definition — needed to blind a token request at all) requires
three headers:

```
X-Atlas-Identity:  <identity id>
X-Atlas-Timestamp: <ms since epoch, at signing time>
X-Atlas-Signature: <base64 Ed25519 signature>
```

The signature is over `${METHOD}\n${path}\n${timestampMs}\n${sha256hex(rawBody)}`,
using the identity's private key — see `domain/auth.ts`'s
`canonicalSigningString`. Routes read the acting identity from
`req.atlasIdentityId` (set by the middleware after verification), never
from a client-supplied id in the request body — see `api/authMiddleware.ts`
and the comment at the top of `api/routes/sources.ts`.

Registration (`POST /identities`) is the one exception: it can't be signed
by an already-registered identity, since it's the act of creating one.
Instead, the client signs a fixed challenge string with the *new* keypair
(`registrationChallenge` in `domain/auth.ts`) to prove it holds the private
key for the public key it's registering — `scripts/smoke.ts` shows the full
client-side flow (generate keypair → sign challenge → register).

## What's been verified, and what hasn't

This sandbox had no Postgres and no Docker available, so here's the honest
line between what's actually been run and what's been type-checked/reviewed
but not executed against a live database:

- ✅ **Schema validity**: `npx prisma generate` succeeds against the full
  schema.
- ✅ **Whole-codebase type correctness**: `npx tsc --noEmit` passes clean
  across domain, adapters, services, and the API layer, on strict mode with
  `noUncheckedIndexedAccess` — including every file that uses Prisma's
  generated types and the real Stripe SDK's types.
- ✅ **Domain logic, for real, with real assertions**: `npm test` runs 28
  passing tests with no database required:
  - Two numerically reproduce the exact fraud scenario from §10 — a
    chargeback landing after the position was released leaves Atlas's
    operating account at exactly `-£1000.00`, proven by summing real
    `LedgerEntry` amounts, not asserted in prose.
  - Eight run real Ed25519 cryptography — generate a keypair, sign, verify,
    confirm cross-identity signatures are rejected, confirm tampering with
    any signed field is detected, confirm stale timestamps are rejected.
  - Five run real RSA blind signatures — a real 2048-bit keypair generated
    by Node's own crypto module, a full blind/sign/unblind/verify round
    trip, a demonstration that blinding the same token twice produces two
    unrelated-looking values, and rejection of forged/cross-issuer
    signatures. No mocked crypto anywhere in any of these tests.
- ⬜ **Live database execution**: `scripts/smoke.ts` runs identity
  registration (with a real generated keypair), a disputed purchase, a
  clean purchase → release → withdrawal, and a full blind-signature
  SpendToken issue → redeem → rejected-double-spend cycle, end-to-end
  through Prisma against a real Postgres instance — but has not been
  executed anywhere, because there's no Postgres in this environment. It's
  been written and type-checked, not run. This is the first thing to run in
  the real deployment environment — see below.
- ⬜ **Real Stripe calls**: `adapters/funding/stripe.ts` has not been
  exercised against Stripe's actual API (no API key in this environment) —
  type-checked against Stripe's real SDK types, not executed.

## Running it for real

Any Postgres works, including a hosted one — Supabase is a reasonable choice
if you don't want to run Postgres yourself: it's Postgres underneath, so
nothing in `schema.prisma` needs to change, just point `DATABASE_URL` at it.

```bash
cp .env.example .env    # set DATABASE_URL to your Supabase (or any) Postgres connection string
npm install
```

Then apply the schema. Two ways to do this:

- **Recommended**: `npm run db:migrate` — runs Prisma's migration workflow,
  which applies everything in `prisma/migrations/` in order and keeps a
  migration history table so it knows what's already been applied.
- **Manual**: open `prisma/migrations/<timestamp>_init/migration.sql` in
  Supabase's SQL editor (or `psql`) and run it directly, then do the same
  for `prisma/seed.sql` to load the reference asset data.

```bash
npm run smoke   # runs scripts/smoke.ts end-to-end against your real database
npm run dev     # starts the API on :3000
```

To exercise the real Stripe adapter instead of the stub, also set
`STRIPE_SECRET_KEY` (and `STRIPE_WEBHOOK_SECRET` for the dispute webhook)
in `.env` — see `.env.example`. Without it, card funding automatically uses
the in-memory stub, so the rest of the system stays runnable with zero
external accounts.

### Deploying on Railway

This repo is a monorepo (`backend/`, `docs/`, `web/` all sit at the root),
and Railway's build system looks at the repo root by default — it won't
find a buildable app there and will fail with "could not determine how to
build the app." Fix this once, in the Railway dashboard, per service:

**Settings → Source → Root Directory → set it to `backend`.**

`railway.json` in this folder then takes over from there (`npm ci && npm run
build` to build, `npm start` to run) — nothing else to configure for the
build itself. What Railway *doesn't* provide automatically is `.env` — it
injects environment variables directly into the process instead of writing
a file to disk, which is also why `npm start` deliberately doesn't use
Node's `--env-file` flag (that flag throws if the file doesn't exist, and
in a deployed container it won't). Set the real values under the service's
**Variables** tab instead, matching what's in `.env.example`:
`DATABASE_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`. `PORT` doesn't
need setting — Railway injects its own and `server.ts` already reads
`process.env.PORT`.

Database migrations aren't run automatically on deploy — run
`npm run db:migrate` from your own machine against the same `DATABASE_URL`
(or run the SQL files directly in Supabase's SQL editor, per above) before
or after deploying; either order is fine since the API only starts serving
traffic once it's already running.

### Adding to the schema over time

This is a real migration history, not a one-off file — the same pattern
used to create the initial migration is how every future schema change
should be made, so `prisma/migrations/` stays an accurate, ordered log of
every change, and `npm run db:migrate` (or a raw SQL run in Supabase) always
brings a database fully up to date regardless of when it was last touched:

```bash
# after editing prisma/schema.prisma:
npx prisma migrate dev --name <what_changed>
```

If there's no live database connection available to generate the diff
against (as was the case while building this in a sandboxed environment),
the same SQL can be produced without one:

```bash
npx prisma migrate diff --from-empty --to-schema-datamodel=prisma/schema.prisma --script
# or, to diff against the *previous* migration instead of from empty:
npx prisma migrate diff --from-migrations=prisma/migrations --to-schema-datamodel=prisma/schema.prisma --script
```

## What's next

In the order it actually needs to happen, per the research doc's build
order:

1. **Run the smoke test against real Postgres** — first real execution of
   the persistence layer, closing the biggest unverified gap above.
2. **Get a Stripe test-mode key and exercise the real adapter** — the code
   exists and type-checks against Stripe's real SDK; it just hasn't made a
   real network call yet.
3. **Replace `adapters/custody/stub.ts`** with a real MPC provider — this is
   what turns "Holdings" from a database row into an actual, real,
   non-custodially-held crypto position.
4. **Replace `adapters/liquidity/stub.ts`** with a real exchange/Circle
   integration — turns the illustrative fixed rates into live market
   execution.
5. **A real Open Banking/PISP adapter** for the bank-funding path. This is
   also the point at which real regulatory/licensing conversations (§10)
   stop being deferrable.
6. **Harden the blind-signature scheme**: move the issuer key behind a KMS
   instead of process memory, adopt RFC 9474-style padding, and add
   per-denomination issuer keys so a redeemed token's amount is
   cryptographically bound instead of trusted at face value — see the
   "Real blind-signature SpendTokens" section above for exactly which
   limitations this closes.

None of this is "tens of thousands of lines" yet — it's a real, correct
foundation sized to be extended into that, not a placeholder pretending to
be one.
